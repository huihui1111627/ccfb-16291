# 剧本杀门店预约：截止时间与取消的传播

一个用 Go 写的服务间调用框架模拟器。37 个服务、同步 RPC 与异步消息混合，把**绝对截止时间**和**取消**从入口一路传到每一跳，并把不传截止时间的做法放在同一份种子、同一份拓扑下做对照。

要证明的事情很具体：前端等三秒就超时，后面的服务不该继续傻干；房间不该锁着没人付款；半夜不该给早就取消的订单发通知。

## 快速开始

```bash
# 1. 跑仿真（默认 20 万请求，两种模式各跑一遍，顺带写出离线核对日志）
go run ./cmd/sim -n 200000 -rate 1200 -checkdir results

# 2. 生成调参扫描数据（可选，页面上的滑杆要用）
go run ./cmd/sweep -n 4000 -rate 1500

# 3. 起页面
go run ./cmd/serve
# 打开 http://127.0.0.1:8099/
```

页面内容：

- **总览**：两种做法并排的八个关键数字（白干处理时间、房间白锁、过期后仍开始、客户端走后仍干活、幽灵订单、过期通知、单次房间最长占用、取消后未清理）。
- **逐请求的调用树**：每一跳一条泳道，红线是该请求的入口截止时刻，右侧写着这一跳开始时还剩多少预算；点开看取消原因、取消决定方、预算收紧的传下来源、清理动作、锁住的房间。可切到“不传截止时间”视图对照同一请求。
- **各服务的账**：到达、开始、完成、取消、排队过期、未发出、处理耗时、其中白干、排队 p99。
- **取消究竟从哪来**：按决策服务和原因汇总。
- **调参与扫描**：拖动入口超时与慢服务延迟，即时看白干工作量、房间白锁怎么变。
- **事后验收**：从日志重放得出的核对结果，而不是信任运行时的计数器。

## 八条要求分别落在哪

| # | 要求 | 实现位置 |
|---|------|----------|
| 1 | 入口给绝对截止时刻，往下扣掉本地已花时间再传；各机器时钟偏差不能算错 | `internal/dlctx` 的 `Wire`/`ToWire`/`FromWire`：线上只传「发送时的剩余预算」和「发送时刻的单调计时」，接收方用自己的单调源减去传输时长。**全程只做时长相减，从不比较两台机器的墙钟**。墙钟只用于展示。 |
| 2 | 剩余时间不够下游最低处理时间，调用干脆不发，本地直接返回超时 | `Sim.issueChild`：`rem - net < minProc` 时不出门，记成 `gated` 并写明理由。 |
| 3 | 上游取消或超时，正在进行的下游马上收到取消，一层层传到底，排队未开始的直接丢 | `Sim.applyCancel` / `cancelChildren` / `requestCancel`：取消沿调用树逐跳传播（按各自链路的延迟），运行中的立刻中断并释放 worker，排队中的从队列里摘除。 |
| 4 | 服务收到取消能执行清理，清理本身有时间上限 | `Sim.startCleanup` / `cleanupDuration` / `cleanupDone`：清理脱离请求预算（请求已经死了也必须跑），但每个动作有硬上限 `CleanupHardCap=250ms`，并单独记账。 |
| 5 | 任何一层可以收紧自己的截止时间，不能放宽 | `dlctx.Deadline.Tighten`：本地预算比上游更紧才生效，否则原样返回；收紧会写进 lineage，页面可追溯。 |
| 6 | 服务端排队按截止时刻排，过期请求出队直接丢，不浪费处理时间 | `dlctx.Queue`（按 deadline 排序、相同 deadline FIFO）+ `Sim.canStart`：出队时若剩余预算连本服务最小处理时间都不够，直接丢弃并计入 `queue_expired`，绝不占用 worker 或房间。 |
| 7 | 截止时间和取消要穿过消息队列，消费者拿到过期消息直接丢 | `dlctx.Publish`/`Consume`（预算在投递时盖章、消费时重算）+ tombstone：请求已放弃的子树，其消息在消费时判定过期或已取消，直接丢弃。 |
| 8 | 页面能调各服务延迟分布和入口超时，看白干工作量怎么变 | 滑杆 + 预生成的 `web/sweep.json`（入口超时 × 服务延迟网格，两种模式）。 |

## 时钟偏差是怎么处理的

线上不传「截止的墙钟时刻」，而传两个来自**同一个单调源**的数：

```
remaining = deadline_mono − now_mono_at_send
sent_mono = now_mono_at_send
```

接收方只做：`remaining −= recv_mono − sent_mono`。这里减的全是时长，不涉及任何一台机器的墙钟。每台服务的墙钟偏差是 ±9 秒（`Sim.hostSkew`，展示用），`TestWireMathIsSkewImmune` 会验证它一丝一毫都影响不到剩余预算。真实部署里这个单调源可以是集群级 TAI tick 或同步的单调纪元。

## 验收入口

```bash
go test ./...              # 全部单元/集成测试
go test ./internal/sim -run TestAcceptanceRun -v   # 端到端对照
go test ./internal/dlctx -v                        # 框架语义
```

`internal/sim/check.go` 会把运行时的四个 CSV 日志（开始、取消、清理、异步消费）**事后重放**，独立于进程内计数器地证明：

- 没有任何处理在请求截止之后才开始；
- 没有任何处理在客户端已经放弃之后才开始；
- 每个需要清理的取消都执行了清理，且没有超过上限；
- 没有一条过期或被取消的消息被消费者处理。

`TestAcceptanceRun` 还会额外断言对照组（不传截止时间）确实出现了「客户端走后仍在干活」和幽灵订单——否则比较没有意义。

## 设计取舍

- **仿真时钟是虚拟的、离散的**，不是真开 goroutine 睡秒表。这样几十万个请求、几百万个 span 能在十几秒内跑完，且完全可复现（`TestRunIsDeterministic`）。
- **两次运行共用同一套随机流**（按 `种子+请求号+span号+用途` 分别抽签），所以两种模式看到的是同一批延迟、同一批业务失败，比较是配对的，不是两次独立抽样。
- **「不传截止时间」是诚实的基线**：每一跳既不继承上游截止时间，也收不到上游取消；每个服务只有自己的租约，所以会一直干到租约到期——这正是要在生产里消灭的行为，而不是人为加倍的坏。
- **房间**建模成一份租约：锁房服务成功即占用，直到订单结清（成功路径）或清理动作执行（失败/放弃路径）才释放；租约到期是最后兜底。白锁时长按「客户端已经不等了」之后的时间算。
